## 1. What are the strengths and weaknesses of an AI-assisted documentation workflow?

**Strengths.** The biggest strength was speed and structure. The AI produced a complete, well-organized README skeleton in seconds, which would have taken me much longer to draft from a blank page. It also knew Markdown conventions well: correct header hierarchy, fenced code blocks with language tags, and tables rendered correctly on the first try. Finally, it worked well as a critic — when I asked it to review its own Markdown for syntax errors and suggest improvements, it caught issues like an inconsistent header level and suggested converting a long list of output files into a table, which made the README noticeably more readable.

**Weaknesses.** The AI's first drafts were generic. The initial README included placeholder sections (such as a "Contributing" section) that made no sense for a small course project, and its example commands referenced files that did not exist until I corrected them. This confirmed the assignment's core rule: every AI output has to be verified. If I had pasted the first draft into GitHub without running the commands and previewing the rendering, I would have submitted documentation that looked professional but was partly wrong. The AI also cannot know project-specific facts — the actual file names, the seed used for the data, the real output tables — so all of that substance had to come from me.

## 2. How did iterative prompting (seed → refinement → critique) improve the final output?

Each stage of the prompt pattern added something distinct. The **seed prompt** ("Explain what sections a good GitHub README for an R data analysis project should include") produced a broad outline with more sections than I needed. The **refinement prompt** ("Revise the sections list so it's concise and uses Markdown headers and bullet formatting" and later "Add sections for Installation, Example Code, and License. Keep tone concise and professional") narrowed that outline into something appropriate for a small project and enforced a consistent tone. The **critique/validation prompt** ("Check the Markdown syntax for correctness and readability" / "Review the Markdown for syntax errors and suggest 2 improvements for clarity") acted as a quality gate: it flagged a missing blank line before a list, which some Markdown renderers require, and recommended a table for the outputs. The same pattern worked for the .Rmd file, where the refinement prompt introduced the `# Purpose` / `## Inputs` / `## Outputs` organization and syntax highlighting. The lesson: a single prompt gets a draft; the sequence gets a document. Comparing the final structure with a real tidyverse README (dplyr) confirmed the iterated version was much closer to professional practice than the seed output.

## 3. What ethical practices did you apply when using AI, and why do attribution and validation matter?

I applied four practices. **Disclosure:** the AI Assistance Declaration appears at the top of every file I am submitting, and the README contains a dedicated AI Assistance Disclosure section naming the tool, the date, the main prompts, and the edits I made afterward. **Validation:** I did not copy any AI output without checking it — I ran `analysis.R` end to end, knitted the .Rmd to confirm every chunk executes, and used GitHub's preview to confirm headers, tables, links, and code blocks render correctly. **Doing my own computation:** the AI was used as a design and writing assistant only; all calculations in the project are executed by my own R code, not generated by the AI. **Privacy:** the dataset is fully synthetic and seeded, so no real or personal data was ever shared with an AI tool.

Attribution matters because it keeps the work honest: my instructor can see exactly what the AI contributed and judge my own contribution fairly, which is the difference between assisted work and plagiarism. Validation matters because AI output is fluent even when it is wrong — polished formatting can hide broken commands or invented details. Taking responsibility for verifying everything is what makes it legitimate to sign the declaration's final sentence: I am responsible for the accuracy and originality of this work.
